# Artificial Memory v0.2.0 — Phase 8.5 Experiment Record: DeepSeek Raid A/B

**Date:** 2026-09-18
**Phase:** 8.5 (DeepSeek-inspired retrieval acceleration) — Experiment Record
**Status:** A1 (candidate-window / gate correctness) complete; D (LLM-quality) and B (3,000-call) pending

---

## 0. Executive summary

A/B experiment on the S4 dataset (440 ingested memories, 10-question E2E subset,
same frozen Scorer, same answer LLM, same 2,000-token budget). Retrieval
strategy is switched by one config field (`RuntimeConfig.retrieval_strategy`),
so every delta below is attributable to the retrieval pipeline alone.

| Finding | Evidence | Verdict |
|---|---|---|
| CSA2-style plan cache (FULL/REINDEX/REUSE) is a **pure win** at equal quality | −21% retrieval p50 (42.15 → 33.17 ms), selection stability 0.00 → 1.00, accuracy unchanged | **supported** |
| The **candidate window** — not the gate — is AM's dominant retrieval bottleneck | frozen level-2 pool = **20 of 440** memories (4.5%) → evidence recall at the pool stage = **0/9 questions** | **AM defect, exposed by the raid** |
| Widening the window monotonically recovers evidence | window 50 → 11%, 100 → 11%, 250 → 78%, 450 → 100% (binary per-question) | **confirmed** |
| HierarchicalGate **is not the culprit** in the frozen configuration | gate never fired: 180 → 180, 450 → 450 (pool ≤ 64 below the gate's no-op threshold) | **exonerated** |
| At a widened window the gate **does** fire and is **too aggressive at `pool_size=64`** | window 450: 3960 → 576 candidates (−85%), but discards **53.9%** of evidence memories | **needs retuning; correctness not yet established** |
| A second bottleneck exists **downstream of candidate generation** | even with the full pool and the gate disabled, budget selection retains only **46.2%** of evidence | **open** |
| Frozen-window arms cannot measure answer quality differences | `classic`/`cache`/`gate` all score exactly `answer_accuracy = 0.1`; the evidence never reaches the context, so the LLM sees nothing to discriminate | **inconclusive at frozen window** |
| Once the evidence **does** reach the context, the dataset discriminates | `gate_wide` (window 450): `answer_accuracy` 0.1 → **0.5**, GT coverage 0.1 → 0.6 — but abstention collapses (1.0 → 0.0, one false positive) | **measurable, with a priced trade** |

Cost measured on the live arm runs (§7): at the frozen window the gate is a
no-op (traffic 200 → 200, context identical to `cache`). At the widened window
the gate fires (4400 → 640) and recovers answers, but costs ~1.7× classic p50
(70.6 vs 42.2 ms) and 2.8× context tokens (1450 vs 521). So "gate enabled" is
not a net win by itself; the useful configuration is *window widened + gate
retuned*, and that configuration's correctness is not yet established.

## 1. What was transplanted (pattern map)

Three DeepSeek V4.1 systems-level design principles were abstracted into
memory-runtime equivalents. AM retrieves discrete memories, not KV tensors, so
each principle became a retrieval-plan mechanism.

| DeepSeek V4.1 | AM equivalent | Module |
|---|---|---|
| CSA2 `Full` / `Reindex` / `Reuse` | `RetrievalPlanCache` — query-family candidate reuse (FULL search / REINDEX re-rank / REUSE replay) | `recall/retrieval_cache.py` |
| Hierarchical Sparse Indexer | `HierarchicalGate` — cheap lexical pre-filter narrowing the candidate pool before semantic ranking | `recall/retrieval_cache.py` |
| SWA Bounded Replay | `EphemeralStore` — non-persistent session scratch, rebuilt from the source log on demand | `recall/retrieval_cache.py` |

Compatibility invariants held throughout:

- `BasicRecallEngine` is **unmodified** (the raid engine is a subclass).
- `RuntimeConfig.retrieval_strategy` defaults to `"classic"` — the frozen behaviour.
- `"deepseek"` is strictly opt-in.
- `EphemeralStore` is **not** wired into the Runtime (deliberate: keeps the
  ablation attributable).

## 2. Method

Shared conditions for every arm: same dataset, same frozen Scorer, same answer
LLM, same 2,000-token budget, same 10-question E2E subset (first question of each
category), answer repeats = 3, latency repeats = 5.

| Arm | Retrieval strategy | Candidate window | Gate |
|---|---|---|---|
| `classic` | `"classic"` | frozen (per-level) | — |
| `cache` | `"deepseek"` | frozen (per-level) | — |
| `gate` | `"deepseek"` | frozen (per-level) | `pool_size=64` |
| `gate_wide` | `"deepseek"` | 450 | `pool_size=64` |

Harness: `scripts/deepseek_ab_small.py` (arms, GT funnel audit, window sweep,
gate-pool sweep, per-answer evidence). Engine hook:
`DeepSeekRecallEngine.candidate_window` — a window override that is `None` for
the frozen per-level behaviour.

Two analysis modes:

1. **Live arm runs** (real LLM, LLM-latency excluded from retrieval timing).
2. **LLM-free ground-truth funnel** (`--gate-audit`, `--window-sweep`,
   `--gate-sweep`): deterministic, scores nothing, and runs with access-stats
   frozen (`Memory.touch` neutralised inside the audit context) so the candidate
   window is the only varying factor in the sweep.

## 3. Metric definitions (read this before comparing numbers)

Two ground-truth metrics appear in the evidence files. They are **not**
interchangeable, and reading one as the other produces an apparent
contradiction (e.g. "after the gate = 100%" vs "gate damage = 53.9%" at the
same window and pool size).

| Metric | Field | Unit | Answers |
|---|---|---|---|
| Funnel rate | `funnel.stage_*` | per **question** (binary) | "does this question still have *at least one* evidence memory?" |
| Evidence recall | `evidence_recall.*` | per **evidence memory** | "what fraction of *all* evidence memories survived?" |
| Gate damage | `gate_damage` | per evidence memory | `(in − kept) / in` at the gate stage |

An "evidence memory" is a store memory whose content contains a ground-truth
term of the question. For `gate_pool=64` and window 450 these read 100%
(per-question) and 46.2% (per-memory) simultaneously: every question *can*
still be answered, but half of its supporting memories were discarded.

## 4. Result A1-a: the candidate window is the primary bottleneck

`BasicRecallEngine._get_candidates` caps each level's store query with a fixed
`limit` and no ranking — the store returns its newest-first slice:

| Recall level | Buckets (resolution, limit) | Measured pool on S4 |
|---|---|---|
| 0 `CURRENT_ONLY` | (any, is_current=True, 50) | 50 of 440 (11.4%) |
| 2 `EPISODE` | (EPISODE, 40) + (SEMANTIC, 20) | **20 of 440 (4.5%)** |

The S4 player queries with `level=2` and all 440 ingested memories are
`SEMANTIC`, so the episode bucket is empty and the entire candidate pool is the
20 newest semantic memories. Everything older is unreachable by construction —
no gate, cache or ranking strategy can recover a memory that never enters the
candidate list.

Evidence (frozen configuration, level 2, gate active but below threshold):

| Question | store → candidates → gate → selected |
|---|---|
| factual_recall-00 | 5/5 → **0/5** → 0/5 → 0/5 |
| multi_session_recall-00 | 3/3 → **0/3** → 0/3 → 0/3 |
| temporal_reasoning-00 | 3/3 → **0/3** → 0/3 → 0/3 |
| knowledge_updates-00 | 4/4 → **0/4** → 0/4 → 0/4 |
| contradiction_handling-00 | 8/8 → **0/8** → 0/8 → 0/8 |
| indirect_recall-00 | 3/3 → **0/3** → 0/3 → 0/3 |
| distractor_resistance-00 | 5/5 → **0/5** → 0/5 → 0/5 |
| compression_recovery-00 | 1/1 → **0/1** → 0/1 → 0/1 |
| reflection_reinterpretation-00 | 7/7 → **0/7** → 0/7 → 0/7 |

Store coverage 100%, candidate coverage **0%**: the **entire evidence set is
lost before the raid mechanisms are even reached**. This also explains why all
three arms scored an identical 0.1 — the context never contained the evidence.

## 5. Result A1-b: window sweep (LLM-free, deterministic)

`--window-sweep` widens the candidate window while keeping the level's
resolution-bucket ratios, with access stats frozen so recency feedback cannot
drift between rows. `None` = the frozen per-level behaviour.

| window | frozen pool | candidates (per-question) | after gate | selected | gate in→out |
|---|---|---|---|---|---|
| `None` (frozen) | 20 | **0.0%** | 0.0% | 0.0% | 180 → 180 |
| 50 | 20 | 11.1% | 11.1% | 11.1% | 450 → 450 |
| 100 | 20 | 11.1% | 11.1% | 11.1% | 900 → 576 |
| 250 | 20 | **77.8%** | 55.6% | 55.6% | 2250 → 576 |
| 450 | 20 | **100%** | 100% | 100% | 3960 → 576 |

Reading:

- The window is the binding constraint, and its effect is non-linear: 100 → 250
  moves coverage from 11% to 78%. A "slightly wider window" is not enough; the
  window has to reach the store.
- The gate only starts firing once the pool exceeds `pool_size` (450 → 900 →
  2250 → 3960). Below that it is an expensive no-op — which is why the frozen
  arms measured 180 → 180 and 450 → 450.

## 6. Result A1-c: gate sweep (is the gate *correct*?)

`--gate-sweep` holds the window at 450 (evidence recall 100% at the pool stage)
and varies `pool_size`. `pool_size=440` is the no-op control (the whole pool
survives).

| gate pool | gate in→out | pool reduction | evidence recall @ candidates | @ after gate | @ selected | gate damage |
|---|---|---|---|---|---|---|
| 64 | 3960 → 576 | 85.5% | 1.000 | **0.462** | 0.436 | **53.9%** |
| 128 | 3960 → 1152 | 70.9% | 1.000 | 0.564 | 0.513 | 43.6% |
| 250 | 3960 → 2250 | 43.2% | 1.000 | 0.615 | 0.513 | 38.5% |
| 440 (no-op) | 3960 → 3960 | 0.0% | 1.000 | 1.000 | **0.462** | 0.0% |

Three separate conclusions, in order of importance:

1. **The gate is destructive at the cheap settings.** At `pool_size=64` it
   removes 85% of the pool but also 54% of the evidence. Lexical Jaccard is a
   weak proxy for semantic relevance on this dataset.
2. **Widening the gate helps but saturates below the control.** 128 → 250 buys
   +5pp of evidence recall for 2× the gate output; neither reaches the no-op
   control (1.000).
3. **A second bottleneck sits downstream.** The no-op control still delivers
   only **46.2%** of evidence to the final selection. With all 440 candidates
   available and no gate, the semantic ranking + 2,000-token budget discards
   more than half the evidence. So the frozen pipeline loses recall in *two*
   independent places, and fixing only the window cannot exceed ~46% by itself.

Note the ordering consequence: at `pool_size=64` gate damage (53.9%) is almost
entirely *absorbed* by the downstream bottleneck (selected 43.6% vs control
46.2%), which is why a destructive gate can look harmless in end-to-end
accuracy. Correctness must therefore be judged on evidence recall, not on the
final answer score alone.

## 7. Result A1-d: live arm runs (real LLM, one run, one condition)

**This section is a single live 4-arm run** — real frozen LLM (phi4-mini), 10
questions, answer repeats 3, latency repeats 5 (n=30 answers per arm),
`dry_run=false`. Evidence: `summary_20260918_194509.json` (plus the per-arm
trace dirs `controlled_20260918_194339/194419/194435/194450` and the run log
`real_4arm_20260918.log`). Earlier partial runs are kept in the locker as
provenance only and are **not** quoted here: `summary_20260918_161229.json`
(first live 3-arm run) and `ab4_run.log` (dry-run 4-arm wiring check). Every
number below comes from the one same-condition run.

| Arm | acc | gt cov | p50 (ms) | p95 (ms) | mean (ms) | ctx tokens | stability | plan tiers | gate traffic |
|---|---|---|---|---|---|---|---|---|---|
| `classic` | 0.1 | 0.1 | 42.15 | 46.44 | 42.50 | 520.9 | **0.00** | — | — |
| `cache` | 0.1 | 0.1 | **33.17** | **35.01** | **30.03** | 522.0 | **1.00** | full=10, reuse=240 | — |
| `gate` | 0.1 | 0.1 | 33.90 | 36.21 | 31.30 | 522.0 | 1.00 | full=10, reuse=240 | 200 → 200 |
| `gate_wide` | **0.5** | **0.6** | 70.64 | 87.29 | 68.23 | 1450.0 | 1.00 | full=10, reuse=240 | 4400 → **640** |

Cross-arm first-repeat selection agreement vs `classic`: `cache` 0.1,
`gate` 0.1, `gate_wide` 0.0.

What this single run establishes:

- **Plan cache (CSA2)**: −21% p50 at identical accuracy, identical context
  size, and — critically — identical accuracy to classic. `full=10` (one per
  question) then `reuse` for every repeat; 0 REINDEX because the runner's
  repeats re-issue the *identical* query text.
- **Selection stability**: `classic` re-ranks from scratch on every call and
  never replays the same selection on this dataset (0.00); the cache replays a
  frozen selection (1.00). Discovered by the harness, not the goal of the
  transplant: the frozen baseline is **not reproducible across repeats**.
- **Gate at the frozen window is a no-op**: 200 → 200 means the gate never
  fired (pool ≤ gate_pool). Its cost profile matches `cache` exactly. See §4:
  the window, not the gate, discards the evidence.
- **`gate_wide` is the first arm that answers questions.** Widening the
  candidate window (50 → all 440) and gating to 64 lifts answer accuracy from
  0.1 → 0.5 and ground-truth coverage from 0.1 → 0.6, while the gate still
  cuts the widened pool by 85% (4400 → 640). Passes gained: factual_recall,
  multi_session_recall, knowledge_updates, distractor_resistance,
  compression_recovery.
- **The recall recovery has a price, and it is abstention.** `gate_wide`
  turns the abstention question into a *false positive* (answered when it
  should have abstained; `abstention_accuracy` 1.0 → 0.0,
  `false_positive_rate` 0.0 → 0.1). Feeding 2.8× more context (1450 vs 521
  tokens) made the LLM confident enough to fabricate. **Widening the window
  trades abstention correctness for recall** — this trade must be priced in
  §10, not ignored.
- **`gate_wide` costs**: ~1.7× classic p50 (70.6 vs 42.2 ms) and 2.8× context
  tokens. Retrieval-only latency excludes LLM time; the answer-LLM time with
  a 2.8× context is *not* included in this table, so the true end-to-end cost
  of the recall recovery is higher than shown here.

## 8. Verdicts

**CSA2 plan cache — supported.** Faster (p50 −21%, 42.15 → 33.17 ms),
deterministic (stability 0.00 → 1.00), no quality regression, and it composes
with the frozen engine without touching it. Safe to keep enabled.

**HSI gate — conditional, correctness unproven.** Not the cause of the recall
problem (it never fired below the pool threshold), but at the settings where it
*did* fire it discarded 39–54% of evidence. Retuning is required, and the tuning
target must be evidence recall at a widened window, not latency.

**Candidate window — AM's own defect, exposed by the raid.** This is the
headline result of Phase 8.5. The DeepSeek transplant did not cause the problem;
it built the instrument that found it. The raid's abstract thesis — *handle the
large space cheaply upstream, then narrow before the expensive stage* — is
exactly what the frozen pipeline fails to do: it front-loads the narrowing into
an unranked `limit=20` store slice.

**EphemeralStore — untouched.** Remains outside the Runtime. Not evaluated here;
reserved for its own Replay-vs-Persist experiment.

## 9. What is NOT concluded

- **Answer quality is only measurable once evidence reaches the context.** At
  the frozen window `classic`/`cache`/`gate` all score exactly
  `answer_accuracy = 0.1` — not because the arms are equal, but because the
  evidence never arrives, so every arm answers the same way. The one arm where
  evidence *does* arrive (`gate_wide`, accuracy 0.5) proves the dataset can
  discriminate, but a single 10-question run is far from statistical support.
- **No gate setting is certified correct.** The sweep bounds the damage; it
  does not show a setting with high gate retention *and* meaningful reduction.
  `pool_size=64` destroys 53.9% of evidence; the no-op control retains only
  46.2% downstream.
- **No end-to-end win is claimed for the gate.** The only configuration that
  recovers evidence (widened window) is currently more expensive than classic
  (~1.7× p50, 2.8× context tokens — and answer-LLM time excluded).
- **The recall/abstention trade is observed, not resolved.** `gate_wide` gains
  4 answer passes and loses abstention (1.0 → 0.0, one false positive). Whether
  this is a gate artefact, a window artefact, or an LLM-propensity effect is
  untested — the ablation (wide window, gate off) has not been run live.
- **3,000-call scaling was deliberately not run.** Running it before fixing the
  window would spend the budget reproducing a 0% candidate-coverage artefact.
- **`EphemeralStore`, MoE-style routing and speculative retrieval are out of
  scope** for this experiment.

## 10. Next steps (agreed order)

1. **A1 follow-up (retrieval correctness, LLM-free).** Tune the gate against
   evidence recall at a widened window; investigate the downstream
   selection/budget bottleneck (46.2% ceiling) — ranking quality or budget size.
2. **D — measurement validity (partially answered, finish it).** The
   `gate_wide` result shows the dataset *can* discriminate once evidence
   reaches the context, so the benchmark is no longer blind. Remaining:
   quantify the abstention regression (live ablation: wide window with gate
   off) and, for the 3,000-call scale, verify the answer LLM passes reliably
   enough for differences to be significant.
3. **B — 3,000-call A/B.** Only after A1 and D: same dataset, same frozen
   Scorer, classic vs cache vs (retuned) gate, reporting recall / precision /
   p50 / p95 / tokens / stability / gate retention / answer accuracy.
